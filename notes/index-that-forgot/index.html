The index that forgot where the questions came from

14 August 2026
Home Notes Research

A graph index is built once, over the vectors you happen to have. Every decision it makes — which neighbours to keep, which long edges are worth the memory — is a bet that future questions will look like the data. That bet is usually silent, and usually fine, and then one day it is not.

The failure is undramatic, which is why it goes unnoticed. Recall does not collapse. It sags: ninety-six per cent becomes eighty-nine, the latency budget absorbs a few extra hops, and the dashboard shows a line that is slightly worse than last month. Nobody files a bug for slightly worse.

A small experiment

Take a million embeddings, build the usual graph, and then ask questions that were embedded by a different model of the same family. The vectors still live in the same space. They are still normalised. They are simply, in aggregate, somewhere slightly to the left.

Query sourceRecall@10Hops (median)
Same encoder0.96241
Sibling encoder0.89163
Sibling, re-entered0.94844

The third row is the whole point. Nothing about the graph changed. The only difference is where the search starts: instead of the fixed entry point chosen at build time, it begins at the medoid of a few hundred cached queries from the last hour. Most of the loss was never a graph problem. It was a starting position problem.

The index is not wrong about the data. It is uninformed about the questions.

Why this is cheap

Re-entering costs a few hundred vectors of memory and one median update per hour. Rebuilding the index costs an afternoon of compute and a deploy. We reach for the second because it is the intervention we have a runbook for, not because it is the one the numbers ask for.

I do not think re-entry is a general answer. It patches the part of the mismatch that looks like translation, and does nothing for the part that looks like a change of shape. But it is a useful reminder that a graph index has two inputs, and we usually only measure one of them.
